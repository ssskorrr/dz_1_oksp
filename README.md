# Сервис записи к специалисту

Курсовая работа по дисциплине «Оптимизация клиент-серверных приложений», этап 1.
Автор: Скориков Кирилл Андреевич, БИСТ-24-ПО-3. Вариант 3. Префикс: `kirill_skorikov`.

Сервис показывает свободные слоты специалистов для выбранной услуги, бронирует время без пересечений и отменяет запись. Сводка рассчитывает загрузку и долю отмен за период. Основные экраны: список записей с фильтром и страницами, карточка записи, сводка. Вход: учебная учетная запись `demo` / `demo`, HTTP Basic на локальном стенде.

## Требования

Python 3.12, PostgreSQL 16.15, Flask 3.1.2, psycopg 3.2.12, psycopg_pool 3.2.8 (1–4 соединения). Зависимости закреплены в requirements.txt, полный список версий в evidence/versions.txt. Docker Compose необязателен: вместо него можно использовать отдельный PostgreSQL.

## Установка и запуск на другой машине

Из каталога исходников, PowerShell:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
Copy-Item .env.example .env
# Укажите пароль локальной учебной БД в .env.
docker compose --env-file .env up -d db
$env:DATABASE_URL = 'postgresql://postgres:changeme@127.0.0.1:55439/kirill_skorikov'
# При изменении пароля замените changeme в строке подключения.
.\.venv\Scripts\python.exe seed.py small
.\.venv\Scripts\python.exe app.py
```

Без Docker создайте базу `kirill_skorikov` в PostgreSQL, укажите реальную строку подключения в DATABASE_URL и выполните последние две команды. seed.py сам применяет schema.sql. Схема также называется kirill_skorikov. Учётная запись PostgreSQL должна иметь право создавать схему в этой базе.

На подготовленном авторском стенде PostgreSQL уже находится в runtime и данные в runtime/data. Запуск: `powershell -ExecutionPolicy Bypass -File .\start.ps1`. Каталог runtime не входит в исходный архив и Git.

## Проверка работоспособности

Открыть http://127.0.0.1:8089, нажать «Войти». Выбрать услугу 1 и специалиста 1, период 01.11.2026–01.02.2027, найти слоты, забронировать свободный слот. Новая запись появляется в списке; повторное бронирование возвращает 409. После отмены слот снова свободен. Карточка показывает связанные сущности, сводка пересчитывается.

## Программный интерфейс

Все `/api/` требуют Basic Auth. Ошибки: `{"error":"описание"}`. На ответах `Cache-Control: no-store`. Даты в параметрах задаются ISO 8601, период полуоткрытый [from,to). В JSON даты сериализуются Flask в HTTP-date, как в интерфейсе; этот формат сохраняется при дальнейшей оптимизации.

| Метод и путь | Параметры | Ответ | Ошибки |
|---|---|---|---|
| GET /api/services | нет | items: id, name, duration_minutes, specialty | 401 |
| GET /api/specialists | нет | items: id, name, specialty | 401 |
| GET /api/bookings | page=1, size=20 (1–100), status=active/cancelled/all | items, total, page, size; связанные имена и время | 401, 422 |
| GET /api/bookings/{id} | id | запись, имя специалиста, услуга, длительность, начало и конец | 401, 404 |
| GET /api/slots | service_id, specialist_id, from, to, page, size | свободные items, total, page, size; при несовпадении специализации пустой список | 401, 404, 422 |
| GET /api/summary | from, to | items по специалистам, total_bookings, cancelled | 401, 422 |
| POST /api/bookings | JSON slot_id, service_id | 201, созданная запись | 401, 404, 409, 422 |
| POST /api/bookings/{id}/cancel | id | 200, запись со статусом cancelled; повторная отмена идемпотентна | 401, 404 |

Пропущенные from/to: 2026-11-01 и 2027-02-01. В summary available_minutes — длительность слотов периода, booked_minutes — суммарная длительность активных услуг; utilization = booked_minutes/available_minutes, cancellation_share = cancelled/total. При нулевом знаменателе результат 0. Слоты учитываются по началу внутри периода. Запись занимает весь выделенный слот; длительность услуги должна укладываться в слот. Слоты и специализации задаются расписанием, редактирования расписания API первого этапа не предоставляет.

## Исходные замеры

При работающем app.py:

```powershell
.\.venv\Scripts\python.exe benchmark.py small
.\.venv\Scripts\python.exe benchmark.py work
```

Каждая операция: 5 прогревочных и 30 измеряемых запросов последовательно, одна учётная запись demo, один стенд. p95 — ближайший ранг ceil(0.95*n). Операции записи измеряются с подготовкой/очисткой вне измеряемого интервала: перед отменой создаётся запись; после бронирования она отменяется. За набор добавляется 70 записей; все они отменены. Итоговые JSON содержат все отдельные измерения, p50/p95/максимум, время на сервере, время SQL и число SQL-запросов.

Заголовки X-Total-Ms, X-DB-Ms, X-DB-Queries формируются сервером. Таймер БД охватывает cursor.execute и получение строк, включая транспорт/декодирование; это время обращения к БД, а не чистый CPU PostgreSQL. X-Total-Ms включает получение соединения из пула, авторизацию, обработчик и JSON; разность с X-DB-Ms включает также SET search_path, commit и накладные расходы. Внешняя HTTP-длительность отдельно включает транспорт и чтение ответа.

Дополнительных индексов, кешей, очередей, фоновой обработки и внешнего хранения файлов на этапе 1 нет. Применены только первичные ключи. Для защиты бронирования используется транзакционная advisory-блокировка по специалисту; это обеспечение корректности, не оптимизация.

Условия PostgreSQL одинаковы на двух объёмах: `max_parallel_workers_per_gather=0`, `jit=off`, стандартные `shared_buffers=128MB` и `work_mem=4MB`. Параллельные исполнители отключены после аварии процесса Windows PostgreSQL (0xC0000005); все итоговые серии повторены целиком с указанными настройками, аварийные серии не входят в результаты. Настройки задаются соединениями, поэтому на другой машине применяются автоматически.
